### 1.1 一个重要的方法论教训

v1.0 假定可以用"逐像素跨图静态性"找到 HUD。**实测证明这是错的**：三张图里只有 0.8% 的像素是静态的，唯一静态连通域只有 760px。

原因：① 游戏世界本身是动态的（树摇、水流、NPC 走动）；② HUD 是**半透明**的，像素随底图变化。

**正确方法**是找**结构**而不是找像素：
- 长直线跨图匹配 → 找到小地图、HP/MP/EXP 条的精确边界（F-02/F-03）
- 圆检测跨图匹配（不同地图）→ 找到固定 UI 圆形元件（F-11）
- 列亮度剖面周期性 → 找到技能键排（F-05）

这个教训已写入第 12 章的方法论，后续标定工具继续沿用。

## 2. 硬约束与风险

### 2.1 环境约束

| 编号 | 约束 | 设计影响 |
|---|---|---|
| C-1 | 红手指云手机，共享 vCPU，性能弱 | 稳态 CPU < 5%；识别算法纯 Kotlin，禁引 OpenCV |
| C-2 | 平台不开放 adb | 配置分发走网络/文件/剪贴板三通道 |
| C-3 | 只能鼠标模拟触屏操作 | 复杂配置在 PC 端完成 |
| C-4 | root 可用性需实测（红手指通常可开） | 必须探测 + 无障碍降级 |
| C-5 | 游戏是 UGC 作品，作者改版频繁 | 保留模板失效探针与重标定能力 |
| C-6 | 云手机上看不到日志 | 钉钉/飞书告警 + 本地日志 + 机内日志页 |

### 2.2 ✅ 已确认：键盘通道可用（情况 A）

**结论：游戏原生支持键盘快捷键**（用户确认：未在红手指中设置过任何按键映射，游戏设置里能看到快捷键）。

| 情况 | 机制 | `input keyevent` | 结论 |
|---|---|---|---|
| **A. 游戏原生支持键盘** | 游戏进程处理 KeyEvent | ✅ 能 | ← **本项目属于此类** |
| B. 红手指客户端按键映射 | 客户端把键盘翻译成触摸事件 | ❌ 不能 | 不适用 |

**架构收益**：
- **技能键坐标完全不需要标定** —— 用 `input keyevent 8/9/10` 直接放技能
- 走位用 `input keyevent 21/22` 直接控制方向
- 出传送门用 `input keyevent 19`（方向键上）
- 整个输入层只剩"发按键"一件事，可靠性大幅提升

**保留触摸通道**仅作兜底（万一某些按键游戏没绑定），不做主力。

### 2.3 仍需 P0 验证：方向键能否持续移动

`input keyevent 21` 是一次**瞬时按下**，而持续行走需要**按住**。四种方案按优先级：

| 优先级 | 方案 | 命令 | 说明 |
|---|---|---|---|
| 1 | **连发** | 以 10Hz 循环发 `input keyevent 21` | 若游戏按"每次按键走一小步"实现则完美，且**可精确控制步数**，天然适配"短步进+每步反馈" |
| 2 | 长按 | `input keyevent --longpress 21` | 保持时长可能受限 |
| 3 | 底层注入 | `sendevent` 写 `/dev/input/eventN` | 最可靠但需按设备映射键码 |
| 4 | 摇杆兜底 | `input swipe` 按住摇杆 | 需要标定摇杆几何 |

**连发方案是首选**：既可控又可测（发 N 次 ≈ 走 N 步），且不需要任何几何标定。

### 2.4 ✅ 已确认：方向键连发可持续移动（F-22）

用户实测确认。这条确认的价值很大 —— 它一次性消除了四个不确定性：

| 原本的风险 | 现在 |
|---|---|
| 连发是否有效？ | ✅ 有效 |
| 是否需要 `sendevent` 底层注入？ | ❌ 不需要 |
| 是否需要标定摇杆几何？ | ❌ 不需要 |
| 是否需要 `--longpress` 的长按支持？ | ❌ 不需要 |

**走位的最终实现**：`input keyevent 21/22` 以 10Hz 连发 N 次，N 由距离估算并封顶，每步后重新截图定位、重新决策。

**副产品**：连发天然可计量 —— "发 15 次大约移动多少像素" 可以在首次运行时**自适应标定**，之后用它做开环估计、再用截图闭环纠偏。比纯闭环快，比纯开环准。

### 2.5 Android 13 / 11 双版本兼容（F-24）

同一份 APK 要同时跑在 Android 13 和 11 上，两者差异集中在这几处：

| 项 | Android 11 (API 30) | Android 13 (API 33) | 本项目的处理 |
|---|---|---|---|
| `POST_NOTIFICATIONS` | 不需要 | targetSdk≥33 才需要运行时申请 | **targetSdk 取 30 → 低版本上自动授予，高版本上被豁免** |
| 前台服务类型 | 宽松 | 强制声明且校验严格 | 仍显式声明 `dataSync`（或 `specialUse`），两边都能过 |
| 精确闹钟 | 需要 `SCHEDULE_EXACT_ALARM`（API 31+） | 同 | targetSdk 30 豁免；但仍声明该权限以备用 |
| 后台启动前台服务 | 受限 | 更受限 | 一律由用户在机内 UI 手动启动，不在后台自启 |
| MediaProjection | 需前台服务 type | 同 | 仅兜底通道用，主通道是 root |
| `su` / SELinux | 宽松 | 更严 | root 只用于 `screencap` 与 `input`，不碰系统分区 |

**结论：`minSdk 26` + `targetSdk 30`。** 这是同时兼容 Android 11 与 13、且规避两代权限收紧的最省事组合。

**保活策略相应简化**：不依赖后台自启，改为「用户手动启动 → 前台服务常驻 → 看门狗重启服务（不重启进程）→ AlarmManager 兜底」。若进程被杀，靠用户或平台侧重新拉起。

### 2.6 root 是开关，需要引导（F-23）

红手指的 root 由用户在平台侧开启。APK 必须处理"root 未开"这一常见首发状态：

```
启动自检:
  su -c id  →  返回 uid=0 ?
    ├─ 是 → 启用 rootShell 通道（主通道）
    └─ 否 → 机内 UI 显示醒目提示：
             "检测到 root 未开启。请在红手指客户端中开启 root 后重试。
              当前将使用无障碍通道（较慢）。"
           → 自动降级到 Accessibility 通道继续可用
```

**降级不是失败**：无障碍通道功能等价，只是截图与输入延迟更高（约 3~5 倍）。这样即使忘记开 root，程序也能跑，只是慢一些。

### 2.4 用户决策带来的风险（已告知，予以保留）

用户决定**不做 BUFF 视觉检测**，理由是"BUFF 很少失效、时长固定"。此决策予以尊重，配置默认 `mode: "timer"`。

**但必须记录风险**：纯定时的真正风险不是"BUFF 时长不准"，而是"**这一次点击/按键根本没生效**"。来源：

| 失效来源 | 后果 | 能否被纯定时发现 |
|---|---|---|
| 游戏卡顿吞输入 | 本次 BUFF 未加 | ❌ |
| 公告/对话框挡住 | 输入落到错误目标 | ❌ |
| 掉线 | 后续全部无效 | ❌ |
| 技能 CD 未转好 | 空放 | ❌ |
| 传错地图 | 在错误地点放技能 | ❌ |

**低成本对策（强烈建议保留，默认开启）：场景守卫。** 不检测 BUFF 图标，只在每次动作前后各采样一帧，确认：
1. 当前处于预期场景（自由市场 / 野外）
2. 屏幕上没有未登记的弹窗

开销 < 1 fps，但能捕获上表中最致命的四类失败。BUFF 图标精细检测仍做成开关、默认关闭。

## 3. 总体架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────────────┐
│ L6 配置分发   HTTPS 拉取 │ 文件导入 │ 剪贴板 Base64 │ 管理端 API(预留)   │
├──────────────────────────────────────────────────────────────────────┤
│ L5 机内 UI    总开关 │ 通道状态 │ 当前场景 │ 下次动作倒计时 │ 日志       │
├──────────────────────────────────────────────────────────────────────┤
│ L4 仲裁       优先级 │ 互斥锁 │ 全局节流 │ 熔断 │ 退避                  │
├──────────────────────────────────────────────────────────────────────┤
│ L3 任务       ScheduledTask(5分钟循环) │ ReactiveRule(弹窗) │ Macro     │
├──────────────────────────────────────────────────────────────────────┤
│ L2 场景       小地图内容锚点 │ 场景投票去抖 │ 场景状态机               │
├──────────────────────────────────────────────────────────────────────┤
│ L1 感知执行   感知: Screencap(root) / MediaProjection / ADB            │
│               执行: KeyInjector(keyevent) → TouchInjector → A11y       │
├──────────────────────────────────────────────────────────────────────┤
│ L0 基础       前台服务 │ 看门狗 │ 保活 │ 日志 │ 告警(钉钉/飞书)          │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 输入通道三级降级

```
KeyInjector (keyevent)          ← 首选，零坐标，最可靠
    │ 不可用（P0 判定为情况 B）
    ▼
TouchInjector (root input tap/swipe)  ← 需要坐标标定
    │ root 不可用
    ▼
AccessibilityInjector (dispatchGesture)  ← 保命通道
```

上层只调 `InputInjector` 接口，运行时自动选择并记录降级事件。

### 3.3 并发模型（沿用 v1.0）

Engine 单线程事件循环做全部决策（无锁、无竞态）；Sensor / Vision(2线程) / Action / Ops 各自独立。决策串行是本项目最重要的架构决定。

## 4. 输入层设计

### 4.1 键盘键位映射

| 动作 | keyevent 码 | 常量名 | 备注 |
|---|---|---|---|
| 技能 1 | 8 | `KEYCODE_1` | 加 BUFF |
| 技能 2 | 9 | `KEYCODE_2` | 加 BUFF |
| 技能 3 | 10 | `KEYCODE_3` | 加 BUFF |
| 技能 4 | 11 | `KEYCODE_4` | 备用 |
| 向左移动 | 21 | `KEYCODE_DPAD_LEFT` | 连发实现持续行走 |
| 向右移动 | 20→22 | `KEYCODE_DPAD_RIGHT` | 同上 |
| 向上移动 | 19 | `KEYCODE_DPAD_UP` | 视需要 |
| 向下移动 | 20 | `KEYCODE_DPAD_DOWN` | 视需要 |
| 确认/交互 | 66 | `KEYCODE_ENTER` | 可能用于传送确认 |
| 取消/关闭 | 111 | `KEYCODE_ESCAPE` | 可能用于关弹窗 |
| 空格 | 62 | `KEYCODE_SPACE` | 视游戏绑定 |

**全部键位做成配置项，不硬编码。** 不同职业的技能数量不同（1~3 个），键位也可能不同。

### 4.2 常驻 root shell（沿用 v1.0 的核心优化）

**绝不每帧新建 `su -c` 进程**（每次 100~200ms）。启动时开一个常驻 `su` shell 持有 stdin/stdout，后续所有命令写一行即可。输入延迟从 ~150ms 降到 ~20ms。

```
stdin.write("input keyevent 8\n")
stdin.write("echo __M7__\n")        # 用标记切分输出，避免回显混杂
```

### 4.3 动作合成

| 动作类型 | 实现 | 参数 |
|---|---|---|
| `key` | `input keyevent <code>` | `code`, `waitAfterMs` |
| `keyRepeat` | 以 `rateHz` 连发 N 次 | `code`, `count`, `rateHz`（默认 10） |
| `keyHold` | `input keyevent --longpress <code>` | `code`, `durationMs` |
| `tap` | `input tap x y`（触摸兜底） | `target`, `jitter` |
| `swipe` | `input swipe ...`（摇杆兜底） | 起终点、时长 |

### 4.4 拟人化（沿用 v1.0）

坐标抖动 σ=0.3% 屏宽；间隔 ±15% 抖动；技能间强制 ≥0.9s 间隔；低概率（3%）插入 300~1200ms 停顿；5 分钟周期带 ±12% 抖动，避免整分整秒。

**注意**：`keyevent` 通道下没有坐标，所以"坐标抖动"不适用，改为**时序抖动 + 按键顺序随机化**（多个 BUFF 无依赖时打乱顺序）。

### 5.1 采样策略

| 场景 | 采样率 | 理由 |
|---|---|---|
| 自由市场等待 | 0.5 Hz | 只需监控弹窗，CPU 最省 |
| 传送/加载中 | 0.5 Hz | 无事可做 |

| 走路中 | 5 Hz | 位置闭环需要及时反馈 |
| 异常/未知 | 2 Hz | 尽快看清状况 |

### 5.2 检测特征库（v2.1 新增，全部经实机验证）

实测得到了三个**高可靠性、颜色硬编码**的检测特征，不再依赖脆弱的模板匹配：

#### 特征 1：HUD 血条 → 判断"游戏是否在正常运行"

```
位置: pixelBox [549, 645, 182, 12]   ROI [0.4289, 0.8958, 0.5711, 0.9125]
颜色: 纯红  BGR(36,36,255)  HSV(h≈0, s≈218, v≈255)
三张图完全一致，填充度 0.99
```
**用途**：① 游戏存活检测（血条存在 = 画面正常）；② 战斗状态判断（HP 下降 = 在挨打）；③ 截图黑屏/异常检测的辅助判据。

#### 特征 2：头顶血条 → **角色屏幕定位**

```
位置: pixelBox [579, 381, 58, 7]（野外）   ROI [0.4523, 0.5292, 0.4977, 0.5389]
颜色: 粉红/纯红  HSV(h≈0-2, s≈230, v≈221)
仅组队且角色在此位置时出现
```
**用途**：给出角色的**屏幕坐标**。配合传送门的视觉特征，比较两者 x 坐标即可决定按左还是按右——**这就是走位闭环**，而且比小地图定位更直接（不需要坐标换算）。

**⚠️ 待确认**：该条是否确为角色头顶血条（已生成 `shots/_analysis/血条放大.png` 供人工确认）。

**阈值鲁棒性**：菜单打开时全屏变暗，该条 V 从 221 → 154。所以判据必须用 **H（色相）和 S（饱和度）**，不能依赖 V。建议 `h ∈ [340,360]∪[0,20]`、`s > 120`、`v > 80`。

#### 特征 3：全屏亮度骤降 → **菜单是否打开**（F-18）

```
正常游戏: 全屏亮度均值 ≈ 141
菜单打开: 全屏亮度均值 ≈  86   （降 39%）
交叉验证: HUD 血条 V 值 253 → 177
```

**这是一个意外收获，而且比找按钮可靠得多。** 之前发现 `正常地图` 与 `菜单` 的小地图完全相同（NCC = 1.0000），说明小地图无法判定菜单——而全屏亮度可以。

```
菜单判定 = (全屏亮度均值 < 基线 × 0.8) 且 (HUD 血条 V 值 < 基线 × 0.85)
基线在启动时自适应学习（取前 30 秒的亮度中位数）
```

**另一个收获：菜单叠加区域已被精确定位。** 对 `正常地图.png` 与 `菜单.png` 做亮度补偿后相减，只剩**一个**连通域：

```
面积=178168px  pixelBox=[1025, 0, 255, 720]  ROI=[0.8008, 0.0, 1.0, 1.0]
```

即**系统菜单 = 屏幕右侧一条竖排面板（右 20%、全高）**。菜单里的"自由市场"按键就在这个面板内，标定范围因此缩到 19.3% 屏面。

#### 特征 4：HUD 血条填充率 → **血量百分比 / 死亡检测**（F-20）

```
判据: HP% = 红色列跨度 / 182
实测: 三张图红色列跨度为 182/182、180/182、181/182  → 满血
     像素填充率 82.8%（差异来自血条边框，故用列跨度而非像素比）
```

| HP% | 判定 | 动作 |
|---|---|---|
| > 30% | 正常 | 无 |
| 5% ~ 30% | 危险 | `WARN` 告警（可选） |
| < 5% 或血条完全不命中 | **疑似死亡** | 连续 3 帧确认 → `FATAL` 告警 + 暂停 |

**额外收益**：这个检测器**零成本**——血条的位置和颜色已经为了"游戏存活检测"标定好了，只需再量一下红色跨度。用户已确认"可能会死，需要处理"，这一项正好补上。

**注意**：死亡时血条可能直接消失而非变成 0%，所以判据要把两种情况都算作疑似死亡。

#### 说明：BUFF 是纯技能，不消耗道具（F-21，非检测特征）

用户确认：BUFF 是技能，**不耗道具**。因此**不需要**做背包/药水库存检测，也**不需要**做"技能放不出来"的兜底检测。死亡是唯一需要额外处理的异常。

### 5.3 场景识别：小地图 + 检测特征组合

```
场景判定优先级（自上而下，先命中先返回）：
  1. 全屏亮度骤降        → 菜单/遮罩层打开（P0_EMERGENCY）
  2. 弹窗模板命中        → dialog
  3. 小地图 NCC 匹配     → freeMarket / field / loading
  4. 全部落空            → unknown（持续 60s 告警）

小地图匹配实测结果（已用 tools/ncc.py 验证）：
              自由市场    正常地图
  自由市场      1.0000     0.2815   ← 区分度极大，可靠
  正常地图      0.2815     1.0000
```

**注意**：小地图**无法**区分"野外"与"野外+菜单"（两者小地图像素完全相同，NCC=1.0），这正是必须引入特征 3 的原因。

**辅助印证**：
- 头顶血条是否存在（组队标志，且可给出角色坐标）
- HUD 血条填充比例（战斗状态）
- 左上文字面板内容（F-04）

## 6. 主循环与调度

### 6.1 用户描述的流程

> 自由市场是等待，加技能需要出自由市场加。一般五分钟补一次。

### 6.2 状态机

```
                ┌───────────────────────────────────────┐
                │                                       │
                ▼                                       │
      ┌─────────────────────┐                           │
 ┌───▶│ S1 WAIT_IN_MARKET   │                           │
 │    │ 自由市场内小范围走动   │                           │
 │    │ 直到距上次BUFF满5分钟  │                           │
 │    └──────────┬──────────┘                           │
 │               │ 时间到（锚定上次BUFF释放时刻）           │
 │               ▼                                      │
 │    ┌─────────────────────┐                           │
 │    │ S2 EXIT_MARKET      │                           │
 │    │ 离开自由市场          │                           │
 │    │ 校验:小地图转为野外     │                           │
 │    └──────────┬──────────┘                           │
 │               │                                      │
 │               ▼                                      │
 │    ┌─────────────────────┐                           │
 │    │ S3 CAST_BUFFS       │  ← 记录 t_cast            │
 │    │ 按键 1..N 逐个释放     │                           │

 │    └──────────┬──────────┘                           │

 │    └──────────┬──────────┘                           │
 │               │                                      │
 └───────────────┘  （下一轮计时从 t_cast 起算 5 分钟）
```

### 6.3 计时锚点（关键设计）

**周期必须锚定在 `t_cast`（BUFF 实际释放时刻），而不是循环起点。** 否则"出市场 + 加载 + 回市场"的耗时会被吞掉，导致周期实际变成 5 分钟 + 往返耗时，随时间漂移。

```
nextDueAt = t_cast + 300000 * (1 + jitter)      # jitter ∈ [-0.12, +0.12]
```

若一轮往返耗时超过 5 分钟（异常），下一轮立即开始并告警。

### 6.4 配置驱动的循环

```json
  "periodMs": 300000,
  "periodJitterPct": 0.12,
  "steps": [

```

### 6.5 自由市场内走动（S1）

用户要求"左右走动一定范围"。实现为连发方向键的短步进 + 每步反馈：

```json
{ "type": "walkRange",
  "axis": "x",
  "from": [0.30, 0.55], "to": [0.45, 0.55],
  "tolerance": 0.025,
  "stepMs": 350,
  "maxIterationsPerLeg": 25,
  "pauseBetweenMs": [800, 2500],
  "onStuck": { "action": "nudgeRandom", "retry": 3 } }
```

**每一段行走都是闭环**：每步后重新从小地图提取角色点定位；连续 5 步未朝目标方向移动 → 判定卡住 → 反向 nudge 解卡 → 仍不动则告警。

**降级**：若头顶血条定位不可用（未组队/未确认），降级为"定时长盲走 + 端点锚点确认"。

### 6.6 进出市场的具体机制（v2.1 确认）

用户确认的机制：

```
进自由市场:
  1. 打开菜单（按键，待确认具体键位；或点击菜单位置）
  2. 选择"自由市场"按键
  3. 校验: 小地图 NCC 切到 freeMarket 模板

出自由市场:
  1. 走位到传送门（用头顶血条定位角色 + 传送门视觉特征，比较 x 决定方向）
  2. 按【方向键上】  →  input keyevent 19
  3. 校验: 小地图 NCC 切到 field 模板
```

对应配置（`config/rules.example.json` 的宏）：

```json
"macro_exit_market": {
  "steps": [
    { "type": "assertScene", "scene": "freeMarket", "timeoutMs": 5000 },
    { "type": "walkTo", "targetRef": "portal", "mode": "keyRepeat",
      "axis": "x", "tolerance": 0.030, "stepRepeatCount": 3, "maxIterations": 30 },
    { "type": "key", "key": "move.up", "waitAfterMs": 800 },
    { "type": "waitScene", "scene": "loading", "timeoutMs": 8000, "onFail": "retry" },
    { "type": "waitSceneGone", "scene": "loading", "timeoutMs": 30000 },
    { "type": "assertScene", "scene": "field", "timeoutMs": 15000, "onFail": "alertAndPause" }
  ]
}
```

**走位到传送门的闭环**（这是 `walkTo` 的具体实现）：

```
1. 截图
2. 检测头顶血条 → 得到角色屏幕 x 坐标  charX
3. 检测传送门视觉特征 → 得到传送门屏幕 x 坐标  portalX
4. if |charX - portalX| < 容差: 到达，结束
5. 方向 = sign(portalX - charX)
6. 连发方向键 N 次（N 由距离估算，封顶防止冲过头）
7. 回到步骤 1，最多 maxIterations 次
8. 连续 3 次检测不到角色血条或传送门 → 判定卡住 → nudgeRandom 解卡 → 仍失败则告警
```

**为什么要分步而不是一次走到底**：云手机帧率波动 + 游戏卡顿会导致实际移动距离与预期不符。每步重新检测、重新决策，把卡顿影响限制在单步内。

#### 实现状态与遗留（v0.24 补记）

上面这套机制**已在 APK 里落地**（`MarketFlow.kt`），但有两处必须说清楚：

| 步骤 | 判定方式 | 状态 |
|---|---|---|

| ② 等菜单出现 | **整屏平均亮度下降 ≥8**（基线在点击前量） | ✅ 已实现，阈值待实机校准 |

**角色定位（血条）**：签名来自实机实测（F-17）——主体纯红渐变 `R195..249 / G0 / B0`，

### 6.7 两种等待模式（v2.1 变更）

用户确认：**"也不一定要去自由市场，也可能原地走动一下"**。因此"等待期待在哪儿"必须做成可配，而不是写死为自由市场。

| 模式 | `waitLocation` | 流程 | 适用 |
|---|---|---|---|
| **简易模式** | `"inPlace"` | 全程待在野外，原地/小范围走动 → 到点 → 原地加 BUFF → 继续走动 | 不需要回城的场景；最短路径，无地图切换风险 |
| **回城模式** | `"freeMarket"` | 自由市场走动等待 → 走到传送门 → 按方向键上出去 → 加 BUFF → 菜单回自由市场 | 需要回城休息/安全的场景 |

```json
"schedule": {
  "mode": "loop",
  "waitLocation": "inPlace",
  "anchor": "afterCast",
  "periodMs": 282000,
  "periodJitterPct": 0.12,
  "steps": [
    { "macro": "macro_wait_and_stroll" },
    { "macro": "macro_cast_buffs" }
  ]
}
```

切换模式只需改 `waitLocation` 与 `steps`，其余不变。**建议先做简易模式**——它没有地图切换，没有加载超时，没有传送门标定，风险面小得多；跑稳之后再决定要不要加回城模式。

### 6.8 计时锚点语义（v2.1 澄清）

用户原话："持续五分钟，然后可以设置多少秒加一次。**不算往返时间。**"

这句话有两种可能的语义，实现差别很大，因此**做成可配**：

| `anchor` | 语义 | 周期公式 | 后果 |
|---|---|---|---|
| `"afterCast"` | 从上一次**释放 BUFF** 时刻起算 | `nextDue = t_cast + period` | **往返耗时算在周期内**。若 period 接近 BUFF 时长，往返期间 BUFF 在倒计时，回到城里时可能已耗尽 |
| `"afterReturn"` | 从**回到等待位**之后才开始计时 | `nextDue = t_return + period` | 往返耗时**额外增加**，实际 BUFF 覆盖 = period，但总循环更长 |

**推荐 `afterCast`**（默认）：它保证"两次释放之间的间隔"稳定等于 `period`，不会随往返耗时波动。用户选定的 `period` 会以"距上次释放多久"直接生效，语义最直观。

**安全余量**：配置里的 `buffProfile.cycleSafetyMarginPct` 会自动把 `period` 压到 `BUFF时长 × (1 - 余量)`。若 BUFF 为 5 分钟、余量 6%，则 `period = 282s`，留出 18 秒吸收往返与抖动。

### 9.3 集控（多设备统一管理）

**实现：Go 单二进制 `altaird` + React 监控台**（旧版是 Python 标准库 + 内嵌 HTML 页面，见本节末尾的迁移说明）。

#### 架构约束：必须是「设备主动上报」

云手机跑在机房 NAT 后面，**没有公网 IP，服务器无法主动连它**。
所以只能反过来 —— 设备定时来敲服务器，指令搭在**上报的响应**里带回去：

```
   控制端（VPS）                                    设备端（云手机 APK）
   ┌────────────────────────────────────┐          ┌──────────────────────────┐
   │ Caddy :443（自动 HTTPS 证书）       │          │ 一轮往返：                │
   │   └─▶ altaird 127.0.0.1:8788       │          │  · 上报状态与心跳         │
   │        ├ go:embed 的监控台 SPA      │ ◀────────│  · 收启停与一次性指令     │
   │        ├ POST /api/v1/device/report │          │  · 执行并在下次上报回执   │
   │        ├ GET  /api/v1/device/config │ ◀────────│ 仅 revision 变化时拉配置  │
   │        ├ POST /api/v1/device/screenshot ◀─────│ 截图上传（点播/主动）     │
   │        └ SQLite（WAL）+ shots/       │          └──────────────────────────┘
   │  浏览器 ──HTTPS──▶ 同源，无 CORS    │
   └────────────────────────────────────┘
```

这个约束顺带把防火墙问题解决了 —— **设备侧只需要能出网**。

#### 协议 v1

**上报** `POST /api/v1/device/report`（`X-Altair-Token` 鉴权）

```json
{
  "deviceId": "a1b2c3d4e5f6", "protocolVersion": 1, "ts": 1699999999999,
  "uptimeMs": 123456, "versionCode": 24, "versionName": "0.24.0",
  "model": "samsung SM-G9910", "android": "13",
  "targetPkg": "com.nexon.mod", "foreground": "com.nexon.mod", "armed": true,
  "appliedRevision": "r17",
  "engine": { "running": true, "state": "WAITING", "cycleCount": 12, "buffs": [] },
  "heartbeat": { "batteryPct": 87, "charging": true, "thermalC": 38.5, "memFreeMb": 1204, "netRttMs": 42 },
  "logTail": ["...", "..."], "ackedCommands": ["c_8f3a"]
}
```

**响应**（关键：一轮往返就把指令带回去）

```json
{
  "ok": true, "ts": 1699999999999,
  "desired": { "running": true, "rev": 7 },
  "configRevision": "r17",
  "nextReportInMs": 30000,
  "commands": [{ "id": "c_8f3a", "action": "screenshot" }]
}
```

**配置** `GET /api/v1/device/config?deviceId=xxx` —— 字段同旧版（`targetPkg` / `pressMs` /
`skillPoints` / `inputMethod` / `buff[]` / `notes`）外加 `desired`。

**截图** `POST /api/v1/device/screenshot` —— multipart，`meta` 是 JSON、`file` 是 jpeg/png，
上限 2MB；落盘 `/var/lib/altair/shots/<deviceId>/`，按「每设备最近 N 张 + TTL」清理。

**指令回执** `POST /api/v1/device/ack`，或直接在下次上报里带 `ackedCommands`（设备端采用后者，省一次往返）。

#### 四个关键设计

1. **合并往返**：v0 每轮固定两次请求（上报 + 拉配置）；v1 把 `desired`、`configRevision`、
   `nextReportInMs`、`commands` 全塞进上报响应 ——
   **启停延迟从「≤1 周期 + 1 次轮询」降到「≤1 个上报周期」，设备流量减半**。
2. **上报周期由服务端下发**（`nextReportInMs`）：面板上改周期即时生效，**不用重发 APK**；
   设备侧只做 `clamp(值, 15s, 300s)`，服务端也钳制。
3. **`rev` 去重**：启停是「期望状态」而非一次性命令，设备只在 `rev` 变化时执行，
   避免每轮重复启停。**`rev == 0` 表示服务端从未下发过，设备必须忽略**
   （旧实现把 `rev=0` 当成"下发停止"，导致新设备一启用集控就被强制停引擎，v1 修掉了）。
4. **只有 `revision` 变化才应用配置并热重载** —— 否则每轮上报都会重写配置、可能打断正在执行的流程。

#### 鉴权（服务要暴露在公网，必须做）

| 访问方 | 方式 | 实现 |
|---|---|---|
| **设备 API** | `X-Altair-Token` 长期 Token | 常量时间比较；失败退避 300ms 并记日志 |
| **面板 API** | **会话 Cookie**（`HttpOnly; Secure; SameSite=Lax`） | `POST /api/v1/panel/login` 换取；token 32 字节随机，**库里只存 sha256 哈希**，可即时吊销 |
| **面板口令** | **argon2id**（PHC 串） | 明文不入库；首次启动生成并只打印一次，忘了用 `altaird set-password` 重设 |
| `/healthz` | 免鉴权 | 探活排障 |

其他防护：登录按 `IP+用户名` 指数退避（前 3 次宽容，之后翻倍，上限 30s）；
审计表记录登录成功/失败、启停、配置变更、Token 轮换；`/api/v1/panel/devices` 是**显式白名单结构**。

> ⚠️ **旧实现有个真实漏洞**：`GET /api/devices` 直接把整个存储返回给浏览器，其中 `auth.panelPass`
> 是**明文面板密码**，每 5 秒往浏览器送一次。v1 白名单 + 哈希存储已修掉，冒烟验收里有专门一项盯着它。

#### 差异化下发

配置按 `deviceId` 分别存放，**没单独配置的设备回退到默认配置** ——
正好对应"不同号不同职业、BUFF 数量和时长都不一样"的实际情况。
每次写入由**服务端生成 revision** 并归档历史版本，支持一键回滚。

#### 监控台能力

设备总览（在线/挂机/轮次统计、状态徽章、**用 `reportTs` 校正时钟偏差的 BUFF 倒计时与进度条**、
心跳、门禁、配置是否生效）、设备详情（上报历史、曲线、日志检索、截图画廊、上报周期）、
配置下发（BUFF 表单 + 版本历史回滚）、审计、设置（设备 Token 显示/复制）。
**实时性靠 SSE**（`GET /api/v1/panel/events`）：设备一上报就推给浏览器，断线自动回落 5s 轮询。

### 14.4 R3 — 时延：⚠️ 截图比预期慢 3~6 倍

| 项 | 实测 | 原预估 | 差异 |
|---|---|---|---|
| 截图（PNG）成功率 | 20/20 | — | — |
| 截图时延 min/中位/p90/max | 173 / **196** / 243 / 248 ms | 30~60 ms | **慢 3~6 倍** |
| 理论最高采样率 | **5 Hz**（纯截图，未含识别） | — | — |
| `input keyevent` 时延 | min 17 / 中位 **20** / max 32 ms | — | ✅ 很好 |

**诊断：瓶颈几乎肯定在 PNG 编码，而非截图本身。** 720×1280 的 RGBA 是 3.5MB，
弱 CPU 上 PNG 编码典型需要 100~300ms；而输出 PNG 仅 191KB，也印证了编码成本高。

**对策（已写入设计）：改用 raw 截图 + 只读 ROI。**

```
raw 模式（screencap 不加 -p）:
  文件 = 16B 头 + w*h*4 字节 RGBA = 3.52 MB
  ├─ 跳过 PNG 编码        ← 省掉主要开销
  └─ 我们只需要两个小区域：
       小地图 ROI 186x134 = 97 KB    ← 直接 seek 读那 134 行
       血条   ROI 182x12  = 8.7 KB
     用 RandomAccessFile 按行 seek，完全不解码整图
```

**预估效果**：截图 196ms → 30~70ms；ROI 读取 1~3ms。**走位闭环从 2.1 步/秒 提升到 3.1 步/秒。**

> 该预估**尚未实测**。probe v0.2 的「③ 采集压测」就是来验证它的：
> 它对比 PNG 与 raw 的时延，并实测 raw 文件上的 ROI 随机读耗时。

### 14.5 采样率设计的最终修正

基于实测（而非预估）重排采样率：

| 场景 | 原设计 | **修正后** | 依据 |
|---|---|---|---|
| 自由市场/野外等待 | 0.5 Hz | **0.5 Hz** | 2000ms/帧，196ms 开销，占空比 10% ✅ |
| 野外加 BUFF 确认 | 2 Hz | **1~2 Hz** | 500ms/帧，占空比 39% ⚠️ 偏紧但可接受 |
| **走位闭环** | 5 Hz | **2.5~3 Hz（raw 优化后）** | PNG 路径下 5Hz 占空比 98%，**不可行** |
| 加载中 | 0.5 Hz | 0.5 Hz | — |

**走位参数随之调整**：单步周期 = 截图(50ms) + 识别(20ms) + 按键连发(250ms) ≈ 320ms，
即约 **3.1 步/秒**。原设计 `stepMs=350`、`maxIterations=30` 覆盖约 9.6 秒行走窗口。
**该参数需在 P1 实测后定稿。**

**架构层面的结论**：`screencap` 的**耗时与分辨率正相关**。若将来换到 1080p 云手机，
PNG 路径会进一步恶化（约 2.25 倍像素量）。**raw + ROI 方案是必须的，不是优化项。**
