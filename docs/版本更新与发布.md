# 版本更新与发布

本文依据 2026-09-26 的构建配置、发布脚本和更新代码整理。整理时 [版本文件](../version.properties) 为 `0.28.6 / 52` 且实现尚未提交；这批改动提交为 `0.29.0 / 53`，发布按第 5 节流程执行，并按第 10 节核对远端证据。下列命令是维护操作说明，文档整理本身不执行签名或发布。

## 1. “推送更新”实际包含什么

发布流程是：准备并提交源码版本 → 校验和构建正式签名 APK → 推送源码 → 创建 GitHub Release → 验证更新源 → 另行提交 CDN 镜像 → 用户点击应用内更新。

客户端不接收远程强制升级指令，也不定期检查更新。用户点“检查并更新”后直接下载 APK，从 APK 中读取 `versionCode`，只有更高版本且包名、签名通过校验才进入安装。没有额外的 `version.json` 或更新服务端需要部署。

| 分发位置 | 用途 | 是否自动完成 |
|---|---|---|
| GitHub Release 的 `probe-release.apk` | 正式更新源，代理源也基于它 | `tools/release.sh` 创建并上传 |
| 仓库 `main` 分支的 `dist/probe-release.apk` | jsDelivr 备用源 | 发布脚本只复制到本地，必须另行审阅、提交并推送 |
| GitHub Actions artifact | CI 的 debug / signed release 构建结果 | CI 上传，但不创建 GitHub Release |
| `dist/probe-release.apk.zip` | 仓库保留的历史文件 | 当前发布脚本不生成、不更新、不上传；客户端不使用 ZIP |

## 2. 准备构建环境

### 2.1 本地发布的现成路径

现有 [工具链脚本](../tools/setup-toolchain.sh) 按 **macOS Apple Silicon** 下载 JDK 和 Android 工具，并在项目 `.toolchain/` 下生成环境文件。不要将它当作跨平台安装脚本直接用于 Linux、Windows 或 Intel Mac。

在项目根目录执行：

```bash
bash tools/setup-toolchain.sh
source .toolchain/env.sh
java -version
./gradlew --version
```

核心组件为 JDK 17、Gradle 8.2、Android platform 33、build-tools 33.0.1，以及 Python 3、Git、`curl` 和 GitHub CLI `gh`。首次安装和首次 Gradle 构建需要网络。

脚本还会尝试安装历史用途的 Go 工具链；虽然当前 Android 模块不依赖 Go，现有脚本该阶段失败仍可能导致安装中止。发布使用的 [构建脚本](../tools/build.sh) 要求 `.toolchain/env.sh` 和 `.toolchain/gradle-8.2/bin/gradle`；仅系统安装了 Gradle，并不能直接满足脚本约定。

`tools/verify.py` 从 `.toolchain/gradle-home` 查找固定版本的 Kotlin 编译依赖。只安装 SDK/JDK 并不足够，应先成功执行一次相关 Gradle 任务以填充缓存。其他平台可自行准备匹配工具运行 Gradle Wrapper，但现成的本地发布流程及离线验证仍有这些目录约定。

### 2.2 GitHub 账号和仓库

```bash
gh auth login
gh auth status
git remote get-url origin
git branch --show-current
```

确认账号具备目标仓库推送和创建 Release 的权限，`origin` 指向预期仓库，当前处于实际分支而非 detached HEAD。现有客户端固定指向 `ecfxs/altair-buff`；正常维护应保持发布目标与其一致。

发布脚本第二个参数可以指定 `owner/repo`，但它不会更改客户端内置更新源，也不会更改 `git push origin` 的目标。不要仅替换这一参数就认为完成仓库迁移。

## 3. 正式签名与版本号

### 3.1 保持原正式签名

已有用户的覆盖升级依赖原正式 keystore。不能为了发新版本临时生成另一把密钥，也不能用 debug APK 替代正式包。

支持两种凭证来源，环境变量优先于本地属性文件：

| 环境变量 | `signing.properties` 对应字段 |
|---|---|
| `ALTAIR_STORE_FILE` | `storeFile` |
| `ALTAIR_STORE_PASSWORD` | `storePassword` |
| `ALTAIR_KEY_ALIAS` | `keyAlias` |
| `ALTAIR_KEY_PASSWORD` | `keyPassword` |

在受控环境注入上述变量，或首次将 [signing.properties.example](../signing.properties.example) 复制为项目根目录的 `signing.properties`，填入已有签名文件路径及凭证；已有配置时直接核对，不覆盖它。`storeFile` 可为绝对路径或项目根目录相对路径，默认位置为 `keystore/probe.jks`。

真实密钥和 `signing.properties` 已由 `.gitignore` 排除，不应放入提交或发布说明。证书 SHA-256 指纹是公开校验值，不是私钥或密码。

签名信任关系需要保持一致：

- `version.properties` 的 `releaseSignerSha256`；
- [strings.xml](../probe/src/main/res/values/strings.xml) 的 `release_signer_sha256`；
- 实际构建 APK 的唯一正式签名证书；
- 使用 CI 正式构建时，仓库变量 `ALTAIR_RELEASE_SIGNER_SHA256`。

当前 Gradle 配置不会自动把版本文件的指纹生成到字符串资源；两个源码值的匹配由验证脚本检查。正常发版不改信任锚。客户端还会比较当前安装包和待安装包的签名，当前实现未开放密钥轮换迁移；debug 包不能直接覆盖升级到正式签名包。

### 3.2 更新已提交版本元数据

在 `version.properties` 修改：

```properties
versionName=0.29.1
versionCode=54
```

这只是相对于本文基线 `0.29.0 / 53` 的示例。正式操作前确认已经分发的最高版本，选择未使用的名称和**更大的整数版本码**，并保留文件中的 `releaseSignerSha256`。

`versionName` 用于显示、发布参数及 `v<versionName>` tag，`versionCode` 决定客户端能否接受更新。只改名称、不增加版本码不会触发升级。脚本不会替你递增版本号，也不自动查询历史最高版本码。

构建允许 `ALTAIR_VERSION_NAME` / `ALTAIR_VERSION_CODE` 环境变量或 `-PaltairVersionName` / `-PaltairVersionCode` 覆盖版本；正式发布应与已提交的 `version.properties` 一致，否则成品验证会拒绝。

## 4. 发布前验证与源码提交

先在项目根目录执行针对性验证：

```bash
source .toolchain/env.sh
./gradlew :probe:automationRegression :probe:lintDebug :probe:assembleDebug --no-daemon --stacktrace
python3 tools/verify.py
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/calibrate -p 'test_*.py' -v
bash -n tools/build.sh tools/release.sh tools/setup-toolchain.sh
git diff --check
```

自动化回归包含动作时序、取消、注入安全和更新下载等检查；离线验证还编译资源并做 DEX 转换。标定服务测试针对保留的本地开发工具。设备上的窗口让路、真实注入、停止、旧版覆盖升级与配置保留仍需实际验证，不能用离线通过代替。

只构建 debug 时可用 `ALTAIR_BUILD_TASKS=assembleDebug bash tools/build.sh`，无需正式凭证。无参数执行 `bash tools/build.sh` 默认同时构建 debug 和 release：缺少正式签名配置时它会在 `verifyReleaseSigning` 门禁处**失败**，不会产出未签名或错签名的 release 包作为替代。

如需在推送前单独查看正式产物：

```bash
./gradlew :probe:verifyReleaseSigning :probe:lintRelease --no-daemon --stacktrace
ALTAIR_BUILD_TASKS=assembleRelease bash tools/build.sh
python3 tools/verify-artifact.py probe/build/outputs/apk/release/probe-release.apk
```

校验脚本输出包名、版本、签名证书指纹及整个 APK 的 SHA-256，需实际读取结果。现有 `dist/` APK 可能落后于源码，不能拿历史文件充当本次新构建。

审阅源码、版本文件和本次文档等实际改动，将属于本次版本的内容逐项提交。示例只展示版本文件的提交方式，源码有修改时需明确列出对应路径一起纳入：

```bash
git diff --stat
git diff -- version.properties
git add version.properties
git diff --cached
git commit -m "发布 0.29.1：更新版本元数据"
git status --short
```

发布前 `git status --short` 应为空；已跟踪文件修改、暂存修改、未忽略的未跟踪文件都会使脚本拒绝执行。本文编写时工作区已有多项未提交修改，因此当前目录并不满足发布前提。不要为达到“干净”状态而丢弃已有工作。

## 5. 执行正式发布

版本已提交、工作区干净、签名及工具链就绪后，执行与版本文件一致的名称，**不带 `v` 前缀**：

```bash
bash tools/release.sh 0.29.1
```

需要明确指定同一目标仓库时：

```bash
bash tools/release.sh 0.29.1 ecfxs/altair-buff
```

两条是替代用法，不要对同一个版本重复执行。该脚本不是预览命令，会实际推送和创建 Release；没有 dry-run 参数。

[release.sh](../tools/release.sh) 的执行顺序如下：

1. 检查版本格式、干净工作区、`gh` 登录，以及版本文件与参数是否一致。
2. 运行 `automationRegression`、`lintRelease` 和 `tools/verify.py`。
3. 构建 release APK，用 `verify-artifact.py` 校验包名、版本、签名；检查成品清单的 HTTPS-only 配置和悬浮窗权限。
4. 确认目标仓库可访问，将**当前分支**推送到 `origin`，再核对远端分支 SHA 等于已验证的本地 HEAD。
5. 若同名 Release 已存在则拒绝继续；否则创建 `v<版本号>` Release，上传 `probe-release.apk`，指定 HEAD 为 tag 目标，再核对 tag 实际落点。
6. 复制同一个 APK 到本地 `dist/probe-release.apk`，不自动提交或推送该文件。
7. 分别下载 gh-proxy、ghfast、GitHub 的 latest APK，与本地产物逐字节比较，并核对版本码和签名。任一失败则返回非零。

脚本仅上传 APK，没有自动生成 ZIP、更新清单或单独校验和资产。Release 说明由脚本填写版本、时间、大小和固定更新地址；详细功能变更说明需要维护者另外准备。

**非零退出不一定意味着尚未发布。** 远端 Release 创建发生在 tag 检查和来源下载校验之前，这些后续步骤失败时，Release 可能已对用户可见；脚本不会自动撤销它。应先检查实际 Release、tag 和资产，不要直接重跑并假设无外部变化。脚本也不会等待 GitHub Actions 全部通过才发布。

## 6. 同步 CDN 备用源

客户端最后一个来源固定读取仓库 **main** 分支的 `dist/probe-release.apk`。发布脚本结束后，先确认本地镜像与本次产物一致：

```bash
cmp probe/build/outputs/apk/release/probe-release.apk dist/probe-release.apk
python3 tools/verify-artifact.py dist/probe-release.apk
git status --short
```

若本次发布确实在 `main` 上完成且当前仍在该分支，审阅后可单独提交镜像：

```bash
git add dist/probe-release.apk
git diff --cached --stat
git commit -m "同步 0.29.1 正式 APK 镜像"
git push origin main
```

若发布来自其他分支，应按仓库流程把经过验证的镜像变更纳入 `main`，不要照搬上述推送命令，也不要以为推送其他分支就能更新 `@main` CDN 地址。镜像提交是发布后的另一个提交，Release tag 仍指向构建所依据的源码提交，这是脚本的正常设计。

提交到 GitHub 后 CDN 仍可能缓存旧内容。下面在保留同一源码版本和本地产物的前提下，下载备用源并校验；成功后删除临时文件，失败则保留现场供检查：

```bash
CHECK_APK=$(mktemp "${TMPDIR:-/tmp}/altair-cdn-check.XXXXXX.apk")
if curl -fL --max-time 120 \
  'https://cdn.jsdelivr.net/gh/ecfxs/altair-buff@main/dist/probe-release.apk' \
  -o "$CHECK_APK" &&
  python3 tools/verify-artifact.py "$CHECK_APK" &&
  cmp probe/build/outputs/apk/release/probe-release.apk "$CHECK_APK"; then
  rm -f "$CHECK_APK"
else
  printf 'CDN 校验未通过，临时文件：%s\n' "$CHECK_APK"
fi
```

发布脚本只自动验证前三个来源，没有替你验证这一步。不要把“镜像已推送”表述为“所有更新源均已更新”。

## 7. 客户端如何取得更新

当前 [Updater.kt](../probe/src/main/java/com/altair/probe/Updater.kt) 内置来源顺序：

| 顺序 | APK 地址 |
|---|---|
| 1 | `https://gh-proxy.com/https://github.com/ecfxs/altair-buff/releases/latest/download/probe-release.apk` |
| 2 | `https://ghfast.top/https://github.com/ecfxs/altair-buff/releases/latest/download/probe-release.apk` |
| 3 | `https://github.com/ecfxs/altair-buff/releases/latest/download/probe-release.apk` |
| 4 | `https://cdn.jsdelivr.net/gh/ecfxs/altair-buff@main/dist/probe-release.apk` |

前三个来源最终取决于 GitHub 的 latest Release，第四个取决于仓库 main。脚本不显式指定 `--latest` 或 `--prerelease`，因此不要仅凭 tag 名称就推断 latest 指向和预发布属性，发布后应核对实际结果。客户端遇到不可达、无效或不够新的 APK 会继续尝试后续来源。

下载实现要求地址及跳转均为 HTTPS，最多跟随 5 次重定向，限制 64 MiB，按单次下载设置 120 秒总时限检查；失败清理半包。多个来源逐一尝试，所以整个更新操作可能超过两分钟。

用户操作为：“停止任务并等待收尾 → 更多 → 检查并更新”。也可填 HTTPS APK 地址或本地 APK 完整路径，用“用指定地址或本地文件更新”。自定义地址保存在单独输入框里，不会替换“检查并更新”的四个内置来源。

安装前确认：有效 APK、包名 `com.altair.probe`、唯一受信任正式签名、与当前安装签名一致、目标版本码高于当前。底层方法虽然有 `force` 参数，当前 UI 始终传 `false`，没有强制重装或降级入口。

Root 模式后台安装脚本写入 `/data/local/tmp/altair_update.sh`，优先通过 `setsid` 启动，不可用时尝试 `nohup`。它稍后执行 `pm install -r -d`，记录退出码，再尝试打开 `MainActivity`。应用界面显示“已启动后台安装”只说明脚本已启动，不是安装完成证明。

重开后查看“更新日志”和实际版本。可在有权限的设备终端查看 `/data/local/tmp/altair_update.log`，检查 `install_exit=0`、包管理器输出及重开结果。安装失败也可能执行重开步骤，不能仅凭应用重新出现判断成功。覆盖安装预期保留应用数据，但需要实际验证；原自动任务不会自行恢复。

无障碍模式不调用 Root 安装：下载/选择 APK 后执行相同信任检查，暂存为应用内部 `pending-update.apk`，保存目标版本和摘要。用户再点“安装已验证更新”，必要时手动允许安装未知应用，返回后重新点安装按钮，在系统安装器确认。非导出的 `UpdateApkProvider` 只授予这一文件的临时只读访问，不开放目录。安装前再次检查摘要、包名、签名及版本；有待安装文件时不覆盖它，必须先安装或丢弃。系统安装不保证自动重开，以用户重新打开后的实际版本为准。

本地文件还可通过“选择本地 APK 文件”授权读取；复制受 64 MiB 大小限制，失败删除半包。普通模式的更新日志保存在应用本地配置中，不读取 `/data/local/tmp/`。上述流程的设备验收事项见 [无障碍兼容与验收](无障碍兼容与验收.md)。

## 8. GitHub Actions 的职责

[ci.yml](../.github/workflows/ci.yml) 对 `main` 的 push 和 pull request 运行 Android 回归、debug lint、标定工具测试、debug 构建，上传 `probe-debug-apk`。

只有 `main` push 且前面的 Android job 成功时，才执行正式签名构建，上传 `probe-signed-release-apk`。需在仓库 Actions 配置中准备：

| 类型 | 名称 | 内容 |
|---|---|---|
| Secret | `ALTAIR_KEYSTORE_BASE64` | 原正式 keystore 的 Base64 内容 |
| Secret | `ALTAIR_STORE_PASSWORD` | keystore 密码 |
| Secret | `ALTAIR_KEY_ALIAS` | 原签名别名 |
| Secret | `ALTAIR_KEY_PASSWORD` | 签名密钥密码 |
| Variable | `ALTAIR_RELEASE_SIGNER_SHA256` | 与版本文件/资源一致的证书指纹，使用小写十六进制 |

CI 将密钥解码到 runner 临时目录并设置 `ALTAIR_STORE_FILE`。缺少秘密或变量时正式构建会失败，不会静默跳过。校验命令固定使用 build-tools `33.0.1`，因此 runner 也必须具备该版本，不能只假定 `setup-android` 保证全部组件存在。

工作流权限为 `contents: read`，没有 `gh release create`、自动打 tag 或提交镜像步骤，也没有声明 GitHub Environment 审批配置。文件里的“Protected” job 名称本身不代表已设置环境审批规则。Actions 构建成功与“用户可下载到新正式版”是两件分别需要确认的事。

## 9. 失败处理与回退

| 问题 | 处理方向 |
|---|---|
| 工作区不干净 | 审阅并提交本次版本所需内容，妥善保留无关工作；不要用重置/删除清空 |
| 版本参数不一致 | 核对命令参数和已提交 `version.properties`；脚本不会自动修改 |
| Release signing 未配置 | 核对密钥文件位置、三个凭证字段及环境变量优先级 |
| 签名信任锚不一致 | 核对版本文件、资源、正式证书及 CI 变量；保留原密钥 |
| 离线依赖缺失 | 先在相同 `.toolchain/gradle-home` 下完成依赖解析，不要把缺缓存判成代码通过 |
| tag / Release 已存在 | 先查真实远端状态；脚本拒绝同名 Release，不覆盖资产；使用新的正式版本，或另行审阅恢复方案 |
| 源码推送失败 / SHA 不同 | 核对分支、权限、远端和实际提交；未通过前不手工绕过发布检查 |
| Release 已创建但下载校验失败 | 检查代理缓存、latest 指向和实际 APK；保留本地产物、摘要与 tag 信息，先确认是否已经对外可见 |
| jsDelivr 仍旧版 | 确认镜像确实进入 main，之后再检查 CDN 缓存和字节一致性 |
| 手机拒绝同版或旧版 | 这是当前 UI 的版本检查；不能靠改 URL 强制覆盖 |
| 安装失败或未重开 | 查更新日志、Root 权限、签名、Android 安装限制及 `setsid`/`nohup` 可用性 |

需要恢复旧功能时，适合现有更新链路的方法是把修复或恢复的代码作为**更高版本码的新正式版**发布。脚本输出的固定历史版本地址可用于取回旧 APK，但当前 UI 会拒绝低版本，不能将该地址宣传为一键回滚能力。手动降级还受 Android 安装策略和数据兼容性约束，应单独制定恢复步骤；不要为解决签名冲突默认卸载用户应用。

## 10. 发布完成的判断

一次完整分发应有可复核证据：源码提交与 tag 对应；APK 包名、版本、正式签名和摘要正确；Release 资产与验证产物一致；主要来源可下载新包；若承诺 CDN 同步，则其字节也应一致；设备覆盖升级后版本和配置符合预期。

本次文档核对了代码路径、参数、命令和链接，未执行上述实际发布及设备升级步骤。此前构建和设备验证的限制见 [复验与验收](复验与验收.md)，用户侧操作见 [主要功能](主要功能.md)。
