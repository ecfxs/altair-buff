# v0.25 简化版设计

> 本文是**当前生效**的设计。历史设计（v2.x，含自动识别、集控、自由市场闭环）见
> [`详细设计.md`](详细设计.md)；集控那一套的设计已归档到 [`archive/集控重构方案.md`](archive/集控重构方案.md)，
> 代码在 v0.25 随简化整体下线。

## 1. 这一版做了什么

从 v0.24.14 的「什么都想做」收敛成**只做两件事**的工具：

| | v0.24 | v0.25 |
|---|---|---|
| 计时 | 单一周期（最短 BUFF 时长 × 0.94），走位只在首轮 | **两套独立计时**：BUFF 每槽位按设置秒数计时；走位独立按设置分钟计时 |
| 坐标来源 | 内置实测值 + 技能带 74px 自动吸附 + 血条定位 | **全部手动标注**，落盘后永久沿用 |
| 输入通道 | 键盘/触摸二选一 | 只有触摸（键盘通道整体删除） |
| 走位 | 左 600ms → 右 600ms | 左 D → 右 2D → 左 D → **等待 1 秒后跳一下** |
| 集控 | 设备上报 / 群控台下发 / 截图上传 | **整体下线**（APK 页 + Go 服务端 + React 面板 + 部署脚本） |
| 场景识别 | 菜单/自由市场/传送点/出口对齐/血条/亮度/黑屏 | **全部删除** |
| 页面 | 运行 / 设置 / 集控 / 日志 | 任务 / 设置 / 更多（含更新与日志）+ 常驻底部操作条 |

**保留不变的**：自动更新（多源容灾）、原地走位、前台门禁、失败熔断、悬浮窗、日志页。

## 2. 功能规格

### 2.1 两套独立计时器

```
启动任务 ──┬── BUFF 槽位 1..4：各自 dueAt = 上次成功 + 设置时长
           └── 走位：walkDueAt = 上次走完 + 间隔（默认 15 分钟）
```

- **启动时两者都立即执行一次**（用户要求：点完启动马上能看到动作，而不是干等 15 分钟）。
- 启动那一刻两者同时到点，实际顺序是**先补 BUFF、再走位** —— 补 BUFF 是主功能，
  先把它做掉；即使随后走位出问题，BUFF 也已经补上了。
- 不再自动乘 0.94：软件设置的秒数就是实际排期，避免界面时间与执行时间不一致。**每槽位独立**，
  所以 280 秒的 BUFF 和 600 秒的 BUFF 互不干扰。

### 2.2 坐标标注（`Picks`）

| 槽位 | 用途 | 缺了会怎样 |
|---|---|---|
| 技能1..技能4 | 补 BUFF 时依次点（只要求**已勾选启用**的那几个） | **拒绝启动**（宁可启动时明确拒绝，也不要每轮静默失败） |
| 跳跃 | 走位结尾点一下 | 走位照走，但不跳（界面与日志都会提示） |
| 轮盘中心 | 推杆原点 | 未标记时拒绝启动，避免移动到错误位置 |

- **必需性只在 `Picks.required()` 里定义一次**：`= 已启用的技能 + 轮盘中心`。
  引擎的启动校验、悬浮窗的启动/标注进度、主界面的准备清单，全部从它派生 ——
  否则很容易出现"悬浮窗说缺 3 项、主界面说缺 2 项"这种自相矛盾。
  `Picks.checklist()` 在此基础上多返回一个"是否必需"标记，界面据此把跳跃显示成可选项。
- 交互：悬浮窗上「标技能N」→ 点画面上那个位置 → 自动保存。**每个槽位独立保存**，
  改一个不会动到其它项。长按某颗技能按钮 = 从这一颗起连续标注；
  「按顺序标记所需位置」= 一路标完所有必需项，标完一项自动接下一项。
- 存储：SharedPreferences `picks`，值形如 `"0.74160,0.56730"`（归一化 0~1），
  另存一个 `${槽位}_screen` = `"宽,高,旋转"`。用文本是为了 `adb shell` 里能直接看懂、能手工改。
- **屏幕校验分三种情况**（`Picks.screenMatch`，纯函数，有回归测试）：
  | 记录 | 判定 | 处理 |
  |---|---|---|
  | 与当前屏幕一致 | `OK` | 直接用 |
  | **没有记录**（v0.25 之前标的 / 从 v0.24 迁移） | `ADOPT` | **按当前屏幕补记**，写一条日志，不拦启动 |
  | 记录的是另一块屏幕 | `STALE` | **拒绝**，要求重新标记 |
  第二行踩过坑：把"没有记录"当成"记录不匹配"，导致老用户一升级就被
  "请在当前游戏画面重新标记"挡住 —— 而重标一次就好，说明屏幕根本没变。
  在用户看来就是**"点启动按钮立马停止"**。
- 启动校验**必须包含屏幕检查**（`Picks.geometryProblem`）：只查"有没有标"的话，
  会先报「✅ 任务已启动」，然后 worker 第一轮把任务停掉，现场看起来像按钮坏了。
- 迁移：v0.24 的坐标（`overlay/pickedPoints` 前 4 项、`market/joyCxMilli,joyCyMilli`）
  首次读取时自动搬过来，老用户不必重标。
- 回显：悬浮窗「回显:开」把标注点画在游戏画面上（只在目标游戏前台时显示）。
  回显层内部用**槽位键**索引，而不是中文标签 —— 标签只是显示文案，改文案不该改配色。

### 2.3 原地走位（`WalkFlow`）

```
① 轮盘左推 D 毫秒
② 轮盘右推 2D 毫秒      ← 双倍：越过原点再往右
③ 轮盘左推 D 毫秒        ← 回到原点
④ 松开轮盘，等待 1 秒后原地跳一下
```

- D 默认 600ms，设置页可调；推杆幅度默认屏宽 6%。
- **纯时长驱动，不截任何图**：曾经用血条 x 闭环回原点，但每步截图与按键抢同一个常驻
  root shell（实机把按键堵成 6 秒一次）。1:2:1 的配比本身就保证回到起点附近。
- 通道由独立的 `TouchAgent` 在单个 root 进程内注入，三段走位共用稳定的触摸时钟；
  注入失败、离开前台、屏幕变化或停止任务都会释放触摸并停止本轮。
- **跳跃未标记时**（可选）走 `walk3` 分支：同样三段 1:2:1，只是不收尾跳、也不多等那 1 秒。
  注入区只覆盖轮盘，不会去点空处。
- **跳跃失败不算整轮失败**：三段走位已经把角色推出去又拉回来了，那一跳只是点缀。
  把它算成失败会让"人已经走完一轮"的战果被一个装饰动作抹掉，还会连锁触发熔断把任务停掉
  （实机日志里正是这个现象）。失败时打一条 `TOUCH_JUMP_FAILED …` 进日志。

### 2.3.1 注入的送达与重试（`GestureSequence`）

触摸的最终落点由系统的 InputDispatcher 决定。它在几种情况下会**丢弃**一次注入并返回
false：目标位置此刻没有可触摸窗口、上一个事件还没派发完、游戏正卡在加载。

- v0.26.4 用的是 `input swipe` 子进程，**从不检查有没有真的送到**，所以这些丢包一直是
  静默的。
- 换成 `injectInputEvent(event, WAIT_FOR_FINISH)` 并检查返回值之后，它们第一次变成了硬失败 ——
  实机表现为「三段走位都成功了，只有最后那一跳被系统拒绝，于是整轮判定失败、任务停止」。

所以每个事件做**有限重试**（3 次，间隔 40ms；取消/中断立即放弃，不浪费次数）。
两个配套约束：

| 约束 | 为什么 |
|---|---|
| DOWN 放在 `try` **之外** | DOWN 自己就被拒时不该再发 UP —— 那等于朝一根没按下去的手指发释放事件 |
| 松手用 `quietSend`（只重试、不抛） | 松手在 `finally` 里，再抛会**盖掉真正的失败原因**，日志指错方向 |

三档失败的处理方式不同，别混：

| 事件 | 被拒时 |
|---|---|
| DOWN | 重试；仍失败 → 整次动作失败（人没动，报错是对的） |
| MOVE | 重试；仍失败 → 整次动作失败（手指还在按着，必须让上层知道） |
| UP | 重试；仍失败 → 只吞掉不报（已在收尾，且不能覆盖真实原因） |
| 收尾的跳跃 DOWN | 重试；仍失败 → 记 `TOUCH_JUMP_FAILED`，**整轮仍算成功** |

诊断：拒绝注入时的错误带**动作与坐标**（`系统拒绝触摸注入 DOWN(1141,614)`）。
只写"系统拒绝触摸注入"的话，远程排查无法区分"按下被拒（人没动）"和"松手被拒（可能卡住手指）"。

### 2.4 安全约束

1. **前台门禁**：只有 `targetPkg` 在前台才动手；不是则记日志并等待回到游戏前台（不计入技能失败）。
2. **失败熔断**：同一槽位连续失败 3 次 → 停止等人工，绝不死循环猛点。
   单次失败按 30s × 连续次数退避重试。

### 2.5 覆盖层在注入时必须「让路」（`InjectShield`）

`input` 注入的触摸由系统按 **z 序**交给最上面那个**可触摸**窗口 —— 悬浮面板/球就浮在游戏之上，
所以只要它盖住了轮盘中心或技能键的位置，注入的 DOWN/MOVE/UP 就全打在**面板自己的按钮**上。

实机现象（用户报告）：展开「工具」后面板变高、正好盖住左下角轮盘，此时点「试走位一次」，
注入的第一个 DOWN 落在面板下部的「复位窗口位置」上 —— 面板当场收起成球，
看起来就是**「一点试走位，悬浮窗自己消失了」**，而角色一步没动（两个症状同一个根因）。

闸门分两档，注入前后由 `Probe` 统一包住（`aroundInject` / `aroundWalk`）：

| 档 | 做什么 | 保证 |
|---|---|---|
| `INJECT`（每次注入） | 覆盖层切 `FLAG_NOT_TOUCHABLE`，**不动几何位置** | 覆盖所有单次点击（补技能），代价最小、用户看不见 |
| `WALK`（整段走位） | 与注入区**重叠**的窗口缩成 1×1 挪到 (0,0) + 置灰，走完按原 x/y/w/h 放回 | **几何事实**，不依赖 ROM 是否正确实现那个 flag |

- 走位必须用 `WALK` 档：轮盘在左下角，而展开后的面板最高能到屏幕 88%，重叠是常态。
- ★ 两档**必须真的分开**。`OverlayService` 绑定时要把 `mode` 透传下去（
  `InjectShield.bind { mode, on, … -> injectGate(mode, on, …) }`）；曾经这里把 `mode` 丢掉、
  两档都按 `WALK` 执行，结果是**每补一个技能，面板就被挪走再放回一次** ——
  一轮 4 个技能就是 4 次可见跳动。回归测试 `injectGate()` 钉住这个契约。
- 恢复兜底：万一某次恢复没跑到，自有窗口会一直带着 `FLAG_NOT_TOUCHABLE`（面板看得见、
  点不动）。空闲时每 2 秒的轮询顺手清一次（`healTouchability`）。
- 采点层一起切 —— 否则任务运行中用户正在标注，引擎的注入点击会被采点层吃掉并
  **静默存下一个错坐标**（正是本项目最忌讳的失败模式）。
- 「面板 ↔ 球」的每次切换都带原因写日志（`▸ 面板 → 球：…`），**走位**档的闸门开合也写
  （`🛡 走位让路：…`）；启动日志带版本号。`INJECT` 档刻意不写日志 —— 它是每次点击都走的
  路径，写了会把真正的结果淹掉。远程排查时这些就是唯一的现场证据。

## 3. 代码结构

```
probe/src/main/java/com/altair/probe/
  MainActivity.kt     三页签（任务 / 设置 / 更多）+ 常驻底部操作条（状态 + 倒计时 + 启停）
  OverlayService.kt   悬浮窗：启停 + 逐项标注 + 标点回显 + 试走位 + 快捷停止
  PickView.kt         全屏标注层（点一下采一个点，自带「取消标注」）
  MarksView           标点回显层（只画标注点，同文件内）
  Engine.kt           两套计时器 + 门禁 + 熔断
  WalkFlow.kt         1:2:1 走位 + 跳（跳跃未标记时只走三段）
  Picks.kt            标注点仓库（唯一坐标来源 + 必需性判定 + 旧数据迁移）
  Probe.kt            底层通道：拉起的触摸进程、前台包名、root 授权
  InjectShield.kt     注入期间让覆盖层让路（INJECT / WALK 两档）
  Updater.kt          多源自更新
  RootShell.kt        一次性 root 命令通道（Activity 与悬浮窗共用）
  ShellCore.kt        全局单例（probe / updater / root）
  LogBus.kt / Busy.kt 日志总线 / 长操作状态（底部操作条订阅它）
  Schedule.java       单个周期任务的排期（纯逻辑，可离线测）
  Actions.kt          动作互斥锁 + 取消令牌
  TouchAgent.java     root 进程里整段执行手势（app_process 入口）
  GestureSequence.java 手势时序（与 Android 解耦，生产与回归测试共用）
  ScreenGeometry.kt   默认显示屏尺寸/方向（标记与注入共用同一坐标系）
  Ui.kt               设计 token + 共用控件（零依赖，手写圆角与水波纹）
```

**零第三方依赖**：并发用 `Thread`，UI 用系统 `Activity`，不引 coroutines / appcompat / core-ktx。

## 5.1 界面结构（v0.28 改版）

```
主界面（Activity）                       悬浮窗（Overlay）
┌──────────────────────────────┐        ┌──────────────────────┐
│ 阿尔泰        [任务][设置][更多] │        │ ▸ 运行中 已运行12:34 ▾│  ← 标题条：拖动 / 点一下收起
├──────────────────────────────┤        │ 补 04:12 · 走 12:30  │  ← 摘要 + 启停**同一行**
│  任务页＝两张卡：                │        │              [▶ 启动] │     按钮 76×34dp
│    ① 当前状态（含最近一条结果）    │        │ ▾ 标记位置      4/6 │  ← 2 行 3 列，格高 25dp
│    ② 准备情况（清单 + 两个按钮）   │        │ [技能1][技能2][技能3] │
│  设置页＝三张卡 + 固定「保存设置」  │        │ [技能4][跳跃][轮盘] │
│  更多页＝悬浮窗与标记 / 更新 / 日志│        │ [  按顺序标记所需位置  ]│
├──────────────────────────────┤        │ ▸ 工具               │
│ ● 运行中  补 04:12 · 走 12:30   │        │ [回显][试走位][复位]  │
│           [启动任务]           │        └──────────────────────┘
└──────────────────────────────┘         56dp 球：色环=状态，中间=倒计时
```

### 配色：中性黑 + 状态色

主界面从"带色深绿"改成**灰阶黑**（`#0A0A0B` 底 → `#141416` 卡片 → `#1E1E21` 控件）。
理由：这个工具只在挂机时扫一眼，界面本身没有需要表达的情绪；加了色调反而每个控件都在抢
注意力。颜色只留给**状态**（绿=正常 / 黄=等待 / 红=故障）—— 屏幕上唯一的彩色就是你该看的那处。
主按钮是**亮面**（`#E9E9EC` + 深色字），黑底上一块白比任何彩色都更像"这里是主要动作"。

悬浮面板是**半透明黑**（`PANEL_BG = #E80D0D0F`，91%）。用纯色会像在游戏画面上贴了张纸；
留一点透明度既看得清字，又隐约透出血条/小地图。透明度是唯一要拿捏的参数：
太低（<70%）压不住亮色画面上的文字，太高就跟纯色没区别。

### 按钮比例

面板浮在游戏画面上，占的每一像素都是挡住的画面，所以按钮一律按"越次要越矮"分三档：

| 档 | 高度 | 用在哪 |
|---|---|---|
| 启停 | 34dp | 主操作，与摘要同行、固定 76dp 宽 |
| 通栏 | 30dp | 「按顺序标记所需位置」 |
| 网格 | 25dp | 「标记位置」6 格 + 「工具」4 格 |

网格那两组一共 10 颗，是面板高度的主要来源；压到 25dp 后整块面板矮掉约 1/4。
格宽仍有 ~70dp，点击区域靠宽度补回来。

### 标题条

- 右侧收起图标 `▾` 用 20dp（原来 13dp 太小，展开后几乎看不出那里能收起）。
- **运行中在状态字后面跟一行小字**「已运行 12:34」（`Engine.runElapsedMs()`）。
  挂机是"开一整天"的用法，用户常要判断"这轮跑了多久、是不是刚重启过"，
  之前只能翻日志里的启动时间自己算。跟着 250ms 的倒计时一起刷新，不额外起线程。
  超过 1 小时格式变 `H:MM:SS`（`Ui.duration`），避免出现 `183:20` 这种读数。

### 反馈

- **底部操作条常驻**：看状态、停任务在任何一页都够得着。改版前启停只在任务页里，
  去设置页改个参数想停任务还得先切回去。
- **顶栏标题与页签同一行**：720p 横屏高度本来就紧，省下的一整行给内容。
- **长操作有进度回显**：底部操作条显示「⏳ 操作名 + 已用秒数」，完成后带时间戳写进日志。
  `Busy` 的状态必须有订阅者，否则 `begin()` 只是往一个没人看的字段里写字。
- **失败原因留在面板上**：`ERROR` 状态下摘要一直显示原因，而不是闪 2.5 秒就退回
  "已停止 · 标注 4/6" —— 后者会让用户以为启动按钮坏了。
